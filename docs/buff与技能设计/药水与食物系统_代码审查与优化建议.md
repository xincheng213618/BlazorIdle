## 🟡 P2 - 剩余优化建议

### P2 #8 - GetAvailableConsumables 方法可优化性能

**问题描述：**  
`ConsumableManager.GetAvailableConsumables` 方法遍历所有物品定义来筛选消耗品。随着物品数量增加，性能可能下降。

**建议优化：**
- 在 `IGameConfigService` 中添加按类型索引的物品查询方法
- 或在 `ConsumableManager` 初始化时缓存消耗品列表

---

### P2 #10 - 消耗品触发条件验证不完整

**问题描述：**  
`items.json` 中配置的 `triggerConditions` 只使用了 `hpBelowPct` 和 `combatStarted`，但设计文档提到的"更多触发条件类型"和"条件组合（AND/OR）"尚未实现。

**当前支持的条件：**
- `hpBelowPct` - HP 百分比低于阈值
- `combatStarted` - 战斗开始时

**建议扩展：**
- 添加 `mpBelowPct`（魔力百分比）
- 添加 `targetHpBelowPct`（目标 HP 百分比）
- 添加条件组合支持

---

### P2 #11 - 槽位唯一性验证可能存在竞态条件

**问题描述：**  
`ConsumableManager.EquipConsumable` 中的槽位唯一性检查和装备操作不是原子性的。但由于 Blazor WebAssembly 是单线程运行的，这在当前环境下不是问题。

**建议：**
- 如果将来移植到服务器端，考虑添加锁机制

---

### P2 #12 - JSON 配置文件缺少架构验证

**问题描述：**  
`consumableSkills.json` 和 `items.json` 中的 `consumableConfig` 没有 JSON Schema 验证。配置错误只能在运行时发现。

**建议：**
- 为配置文件添加 JSON Schema 定义
- 在构建时或加载时验证配置完整性

---

### P2 #13 - 缺少消耗品使用统计

**问题描述：**  
设计文档后续优化建议中提到的"消耗品使用统计"未实现。无法追踪玩家的消耗品使用习惯和消耗速度。

**建议：**
- 在 `CharacterData` 或单独的统计类中添加消耗品使用记录

## ✅ 实现亮点

以下是当前实现的优秀之处：

1. **引用模式设计** - 槽位只保存物品 ID 引用，使用时实时从背包扣除，设计优雅
2. **完善的测试覆盖** - **127 个测试**覆盖了各种边界情况
3. **良好的代码注释** - 中英双语注释，便于理解
4. **事件驱动架构** - 库存变化、消耗品使用都有事件通知
5. **战斗锁定机制** - 战斗中禁止修改配置的设计合理
6. **槽位唯一性验证** - 防止同一物品装备多个槽位
7. **类型安全枚举** - `ConsumableCategory` 枚举提供类型安全的分类判断
8. **可维护的常量定义** - 槽位 ID 通过静态常量数组统一管理
9. **分类配置文件结构** - 物品配置按类型分离到 `Config/items/` 文件夹
