# 离线战斗系统设计文档 - 第一部分：概述与架构

## 1. 需求概述

### 1.1 核心需求
本设计旨在为BlazorIdle游戏添加离线战斗功能，使玩家在离线期间仍能获得收益，并在重新上线时无缝恢复战斗进度。

### 1.2 功能要点
1. **完整状态保存**：心跳服务（30秒）保存完整战斗状态，包括：
   - 当前副本ID和波次
   - 敌人状态（血量、攻击进度等）
   - 玩家角色状态
   - 战斗时间戳

2. **离线收益计算**：
   - 使用真实战斗模拟，非估算
   - 基于上次保存的状态继续推进
   - 快速演算离线期间的战斗进程
   - 恢复到当前应有的战斗状态

3. **时间偏差修正**：
   - 检测本地时间与游戏时间差异（>5秒触发）
   - 自动追赶战斗进度
   - 防止切换标签页/后台导致的进度损失

4. **顶号功能**：
   - 同一账号多端登录时，后登录踢掉先登录
   - 实时通知被踢用户
   - 防止数据冲突

5. **数据管理**：
   - 版本控制：软件更新导致数据不兼容时自动删除旧数据
   - 自动清理：定期删除过期的游戏状态记录
   - 可扩展：支持未来新增的游戏活动（挖矿、伐木、生产等）

### 2.2 核心组件说明

#### 2.2.1 前端组件
- **BattleDemo（战斗组件）**：
  - 负责战斗UI展示和用户交互
  - 检测时间偏差，触发状态恢复
  - 接收并应用恢复后的战斗状态

- **HeartbeatService（心跳服务）**：
  - 每30秒保存角色数据和游戏状态
  - 调用后端GameState API保存状态
  - 处理保存失败的重试逻辑

- **StateRecoveryService（状态恢复服务）**：
  - 登录时获取上次保存的游戏状态
  - 计算离线时长，调用后端模拟离线战斗
  - 应用模拟结果到当前战斗实例
  - 处理时间偏差检测和自动追赶

#### 2.2.2 后端服务

- **GameStateService（游戏状态服务）**：
  - 保存和读取游戏状态
  - 管理状态版本控制
  - 自动清理过期状态

- **SessionService（会话服务）**：
  - 管理用户登录会话
  - 实现顶号功能
  - 会话心跳检测

- **OfflineBattleSimulator（离线战斗模拟器）**：
  - 加载保存的战斗状态
  - **复用 `BlazorIdle.Shared` 中的战斗引擎**（`DungeonManager`、`BattleInstance` 等）
  - 执行快速战斗模拟（无渲染模式）
  - 计算战斗结果和掉落物
  - 返回最终状态
  - **注意**：与前端使用完全相同的代码，无需重复实现

### 2.3 数据流

#### 2.3.1 状态保存流程
```
玩家战斗 → 每30秒触发心跳 → 
提取当前战斗状态 → 序列化为JSON → 
调用GameState API → 保存到数据库
```

#### 2.3.2 离线恢复流程
```
用户登录 → 检查上次游戏状态 → 
计算离线时长 → 调用模拟器 → 
快速推进战斗 → 计算收益 → 
返回当前应有状态 → 恢复战斗显示
```

#### 2.3.3 时间偏差修正流程
```
检测本地时间 → 对比游戏时间 → 
偏差>5秒 → 调用追赶API → 
快速模拟缺失时间 → 更新战斗状态
```

#### 2.3.4 顶号处理流程
```
用户B登录 → 检查用户A已在线 → 
创建新会话 → 将用户A会话标记为失效 → 
通过SignalR通知用户A → 
用户A强制断开连接
```

## 3. 技术选型

### 3.1 数据库
- **SQLite**：已有选型，轻量级，适合单机游戏
- **EF Core**：ORM框架，简化数据访问

### 3.2 实时通信
- **SignalR**（推荐）或**轮询**：用于顶号通知
  - SignalR：实时性好，但需要额外配置
  - 轮询：简单但有延迟，适合简单场景

### 3.3 序列化
- **System.Text.Json**：.NET原生，性能好
- JSON格式存储游戏状态，便于版本控制和调试

### 3.4 战斗模拟与代码复用
- **战斗逻辑共享架构**：
  - 将 `BlazorIdle/Game` 目录下的战斗引擎迁移到 `BlazorIdle.Shared` 项目
  - 包括：`BattleInstance`、`DungeonManager`、`MultiBattleInstance`、`RngContext`、`Clock` 等
  - 前端（Blazor WebAssembly）和后端（ASP.NET Core）都引用 `BlazorIdle.Shared`
  - **真正的代码复用**，无需在服务器端重复实现战斗逻辑
  - 通过加速时钟快速推进战斗（无渲染模式）

**迁移建议**：
```
BlazorIdle/Game/              →  BlazorIdle.Shared/Game/
├── BattleInstance.cs         →  ├── BattleInstance.cs
├── DungeonManager.cs         →  ├── DungeonManager.cs
```

## 4. 版本控制策略

### 4.1 状态版本号
每个游戏状态记录包含版本号，格式：`主版本.次版本.修订号`

示例：
- `1.0.0`：初始版本
- `1.1.0`：新增挖矿功能
- `2.0.0`：战斗系统重构（不兼容）

### 4.2 兼容性检查
- 保存状态时记录当前软件版本
- 加载状态时比较版本号
- 主版本不同：删除旧状态，从当前状态开始
- 次版本不同：尝试兼容加载，失败则删除
- 修订号不同：完全兼容

### 4.3 版本号存储位置
```csharp
public class GameState
{
    public string Version { get; set; } = "1.0.0"; // 软件版本
    public int SchemaVersion { get; set; } = 1;    // 数据结构版本
}
```

## 5. 性能考虑

### 5.1 模拟性能
- **混合策略**提升性能和用户体验：
  - **短时间偏差（< 5分钟）**：客户端本地快速推进，无需服务器调用
  - **中等离线（5分钟 - 1小时）**：客户端模拟，服务器仅验证结果（可选）
  - **长时间离线（> 1小时）**：服务器端模拟，返回最终状态
- 离线战斗模拟使用无渲染模式
- 使用更大的时间步长（如100ms）
- 限制最大模拟时长（如24小时）
- 异步执行，不阻塞UI
- **代码共享**：前后端使用相同的 `BlazorIdle.Shared` 战斗引擎，保证一致性

### 5.2 数据库性能
- 状态数据添加索引（CharacterId, StateType）
- 定期清理过期数据（建议保留7天）
- 使用连接池避免频繁连接

### 5.3 网络优化
- 状态数据压缩（可选）
- 增量更新（仅发送变化部分）
- 批量操作（如批量保存多个状态）

## 6. 安全考虑

### 6.1 防作弊
- 服务器端验证所有状态转换
- 时间戳验证，防止时间回滚
- 状态哈希校验，防止篡改
- 限制离线收益上限

### 6.2 数据保护
- 状态数据与用户ID绑定
- 严格的权限检查
- 防止SQL注入（使用参数化查询）

### 6.3 会话安全
- JWT Token验证
- 会话过期机制
- 防止会话劫持

## 7. 错误处理

### 7.1 状态损坏
- 检测到损坏的状态数据时删除
- 回退到安全的默认状态
- 记录错误日志供调试

### 7.2 模拟失败
- 模拟器异常时返回上次保存的状态
- 不给予离线收益但不丢失数据
- 记录失败原因

### 7.3 网络问题
- 心跳失败自动重试（3次）
- 状态保存失败保留在本地
- 下次成功连接时补发

## 8. 可扩展性

### 8.1 新活动类型
设计支持多种游戏活动：
- `StateType = "Battle"`：战斗
- `StateType = "Mining"`：挖矿
- `StateType = "Woodcutting"`：伐木
- `StateType = "Crafting"`：生产

每种类型使用独立的状态数据结构和模拟器。

### 8.2 未来优化
- 支持多角色并行活动
- 服务器端离线模拟（减少客户端负担）
- 状态快照和回滚功能
- 更复杂的离线收益公式
