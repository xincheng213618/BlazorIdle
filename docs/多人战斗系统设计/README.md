# 多人战斗系统设计文档

## 文档概述

本文档集提供了BlazorIdle游戏多人组队战斗系统的完整设计方案。该系统专为放置/挂机类游戏设计，支持多人组队副本战斗，同时保持离线挂机的游戏特性。

## 核心特性

- ✅ **多人组队挂机**：3-5人组队进行副本战斗
- ✅ **离线收益**：队员可以离线，上线后领取收益
- ✅ **低延迟要求**：不需要即时操作，适合异步更新
- ✅ **代码复用**：复用现有的 `MultiBattleInstance` 战斗引擎
- ✅ **防作弊**：多层验证+服务器托管保障公平性
- ✅ **简化实现**：避免复杂的SignalR，使用REST API + 轮询

## 推荐架构：混合客户端-服务器模式

### 核心思路
- **队长客户端**作为"主机"运行战斗（本地）
- **定期同步**战斗快照到服务器（每30秒）
- **服务器验证**快照并分发收益给所有队员
- **队长离线时**，服务器自动接管战斗（托管模式）
- **队员客户端**轮询查看战斗进度（每60秒）

### 架构优势
- 🚀 **低服务器负载**：队长在线时服务器只做验证
- 🎮 **队长体验好**：本地运行，实时反馈
- 😌 **队员无压力**：可以离线，收益照常
- 🔒 **防作弊完善**：服务器验证+托管兜底
- 📈 **高可扩展性**：单服务器可支持100+队伍

## 设计亮点

### 1. 代码复用 ✨
前后端使用相同的战斗引擎（`BlazorIdle.Shared`），无需重复实现战斗逻辑。

### 2. 混合架构 ✨
队长在线时客户端运行战斗，服务器只做验证；队长离线时服务器接管。完美平衡性能和安全。

### 3. 异步多人 ✨
60秒轮询适合挂机游戏节奏，无需复杂的实时通信，大幅降低实现难度和服务器负载。

### 4. 离线友好 ✨
所有队员都可以离线，战斗继续进行，上线后领取收益。真正的"挂机"多人游戏。

### 5. 防作弊完善 ✨
多层验证（时间、进度、伤害）+ 服务器托管兜底，确保游戏公平性。

## 常见问题

### Q1: 为什么不用SignalR？
A: SignalR适合需要即时反馈的游戏（如动作游戏）。放置/挂机游戏不需要即时操作，60秒轮询已足够，且大幅简化实现。

### Q2: 60秒延迟玩家会不会不满意？
A: 挂机游戏的玩家不需要实时操作，能看到队友在战斗已经很好。况且队长看到的是实时的。类比其他挂机游戏，许多是"关游戏"后才结算收益，我们的体验已经好很多。

### Q3: 队长负担会不会太重？
A: 队长离线>5分钟自动转服务器托管，不会因为队长不在而停摆。而且队长可以享受"主机"的流畅体验，也可以设置队长专属奖励。

### Q4: 如何防止作弊？
A: 多层防护：
1. 服务器验证所有快照（时间、进度、伤害）
2. 检测到异常立即转服务器托管
3. 服务器托管模式下完全权威
4. 可选：战斗录像重放验证

### Q5: 服务器负载会不会太高？
A: 不会。队长在线时，服务器只做验证，几乎无负载。只有队长离线时才运行战斗。单服务器可支持100+队伍，其中大部分时间队长是在线的。
