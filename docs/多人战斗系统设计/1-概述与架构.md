# 多人战斗系统设计 - 第一部分：概述与架构

## 1. 需求概述

### 1.1 核心需求
设计一个适合放置/挂机类游戏的多人组队战斗系统，允许多个玩家组队进行副本战斗，同时保持离线挂机的游戏特性。

### 1.2 关键特性
1. **多人组队挂机**：玩家组队后可以挂机战斗，无需实时操作
2. **离线收益**：队伍中的玩家可以离线，队友继续战斗，上线后结算收益
3. **副本战斗**：复用现有的多V多战斗逻辑（`MultiBattleInstance`）
4. **低延迟要求**：不需要即时反馈，适合异步更新
5. **简化实现**：避免复杂的SignalR实时推送，使用更简单的方案

### 1.3 设计目标
- ✅ 复用现有战斗引擎（`MultiBattleInstance`、`DungeonManager`）
- ✅ 支持3-5人组队战斗
- ✅ 离线玩家自动挂机，收益正常结算
- ✅ 实现简单，易于维护
- ✅ 避免高延迟轮询和复杂的实时通信

## 2. 架构方案对比

### 2.1 方案A：混合客户端-服务器模式（推荐）⭐

**核心思路**：队长客户端作为"主机"运行战斗，定期同步到服务器，服务器验证和分发收益。

**架构**：
```
队长客户端（主机）
├── 运行完整战斗模拟（使用BlazorIdle.Shared引擎）
├── 包含所有队员的角色数据
├── 每30秒上传战斗快照到服务器
└── 队长离线时，转移到服务器端托管

服务器
├── 验证战斗快照的合法性
├── 存储队伍战斗状态
├── 分发收益给所有队员
├── 队长离线时接管战斗模拟
└── 提供API给队员查询进度和收益

队员客户端
├── 只读方式查看战斗进度
├── 可以离线，不影响战斗
├── 上线时从服务器拉取收益
└── 查看战斗日志和统计
```

**优势**：
- ✅ 低服务器负载（只有队长在线时服务器不模拟）
- ✅ 低延迟（队长客户端本地运行）
- ✅ 简单实现（复用现有单机战斗逻辑）
- ✅ 支持离线挂机（队员离线不影响）

**劣势**：
- ⚠️ 队长负责更重（需要一直在线或频繁上线）
- ⚠️ 需要防作弊验证（服务器验证战斗结果）

### 2.2 方案B：纯服务器权威模式

**核心思路**：所有战斗在服务器端运行，客户端轮询获取状态。

**架构**：
```
服务器
├── 为每个队伍运行战斗模拟
├── 使用BlazorIdle.Shared引擎
├── 持续推进战斗（后台任务）
└── 客户端轮询获取状态更新

客户端
├── 30-60秒轮询一次战斗状态
├── 显示战斗进度和日志
└── 接收收益结算
```

**优势**：
- ✅ 完全权威，无作弊风险
- ✅ 队长队员平等，无特殊职责
- ✅ 实现简单直接

**劣势**：
- ❌ 服务器负载高（所有队伍都在运行）
- ❌ 延迟高（30-60秒才能看到更新）
- ❌ 用户体验较差

### 2.3 方案C：镜像影分身模式（备用方案）

**核心思路**：使用其他玩家的角色快照作为AI队友，实际上是单人战斗。

**架构**：
```
客户端
├── 从服务器获取其他玩家角色数据快照
├── 本地运行战斗（使用快照数据作为队友）
├── 战斗结果只给当前玩家
└── 各玩家独立战斗，互不影响

服务器
├── 提供角色快照数据
├── 管理"假组队"关系
└── 各玩家独立结算收益
```

**优势**：
- ✅ 实现极简单
- ✅ 无延迟问题
- ✅ 无同步复杂度

**劣势**：
- ❌ 不是真正的多人战斗
- ❌ 无法共享收益和体验
- ❌ 缺乏社交感

## 3. 推荐方案详细设计（方案A：混合模式）

### 3.1 核心概念

#### 3.1.1 队伍角色
- **队长（Party Leader）**：创建队伍，负责运行战斗模拟（在线时）
- **队员（Party Member）**：加入队伍，只读观察战斗，可随时离线
- **托管模式（Hosted Mode）**：队长离线时，服务器自动接管战斗

#### 3.1.2 战斗模式
- **队长在线模式**：队长客户端运行战斗，定期同步快照到服务器
- **服务器托管模式**：队长离线超过5分钟，服务器自动接管战斗
- **队伍解散模式**：队长长时间离线（如24小时），队伍自动解散

### 3.3 核心数据流

#### 3.3.1 队伍创建流程
```
1. 队长发起创建队伍
   → POST /api/party/create
   
2. 服务器创建队伍记录
   → 生成 PartyId
   → 队长自动加入队伍
   
3. 队长邀请其他玩家
   → POST /api/party/{partyId}/invite
   
4. 其他玩家接受邀请
   → POST /api/party/{partyId}/join
   
5. 队长选择副本并开始战斗
   → POST /api/party/{partyId}/start-dungeon
   → 服务器返回所有队员的角色数据
   
6. 队长客户端开始运行战斗
   → 本地创建 MultiBattleInstance
   → 包含所有队员的角色
```

#### 3.3.2 战斗同步流程（队长在线）
```
队长客户端：
每30秒执行：
1. 提取当前战斗快照
   - 副本进度（当前波次）
   - 所有角色血量、状态
   - 战斗统计（伤害、击杀）
   - 掉落物记录

2. 上传到服务器
   → POST /api/party/{partyId}/sync-battle
   
3. 服务器验证快照
   - 检查时间戳合理性
   - 检查伤害数值合理性
   - 检查进度合理性
   
4. 分发收益给队员
   - 更新 PendingRewards 表
   - 记录每个队员的待领取物品

5. 返回确认
   → 队长继续战斗
```

#### 3.3.3 队长离线处理流程
```
1. 队长断线或离线超过5分钟
   
2. 服务器检测到队长心跳超时
   → PartyHostingService 检测
   
3. 服务器启动托管模式
   - 加载最后一次战斗快照
   - 重建 MultiBattleInstance（服务器端）
   - 继续推进战斗
   
4. 后台任务持续运行战斗
   - 每30秒推进一次
   - 记录收益
   - 更新战斗状态
   
5. 队长重新上线
   - 服务器检测到队长心跳恢复
   - 发送当前战斗快照给队长
   - 队长客户端恢复战斗控制
   - 服务器停止托管
```

#### 3.3.4 队员观战流程
```
队员客户端：
每60秒执行：
1. 轮询战斗状态
   → GET /api/party/{partyId}/battle-status
   
2. 服务器返回：
   - 当前副本进度
   - 战斗统计
   - 最近战斗日志（最近100条）
   - 待领取收益数量
   
3. 客户端更新UI显示
   - 显示进度条
   - 显示战斗日志
   - 显示收益提示
   
4. 玩家领取收益
   → POST /api/party/{partyId}/claim-rewards
   → 收益添加到背包
```

### 3.4 核心优势

#### 3.4.1 性能优势
- **低服务器负载**：队长在线时，服务器只做验证和分发，不运行战斗
- **可扩展性强**：单服务器可支持大量队伍（队长在线时几乎无负载）
- **低延迟**：队长看到的战斗是实时的（本地运行）

#### 3.4.2 用户体验优势
- **队长体验好**：实时战斗反馈，无延迟
- **队员无压力**：可以离线挂机，收益照常结算
- **离线友好**：所有玩家都可以离线，战斗继续进行

#### 3.4.3 技术优势
- **复用现有代码**：直接使用 `MultiBattleInstance` 和 `DungeonManager`
- **实现简单**：无需SignalR，普通REST API即可
- **防作弊**：服务器验证战斗快照，异常则转服务器托管

## 4. 关键设计决策

### 4.1 为什么选择混合模式？

**对比纯服务器模式**：
- 纯服务器模式下，所有队伍战斗都在服务器运行，负载太高
- 即使只有100个队伍，服务器也需要持续运行100个战斗实例
- 混合模式下，队长在线时服务器几乎无战斗负载

**对比纯客户端P2P模式**：
- P2P模式实现复杂，需要NAT穿透、同步协议等
- 混合模式更简单，队长客户端就像"主机"，服务器验证即可

### 4.2 为什么60秒轮询可以接受？

放置/挂机游戏的特点：
- 玩家不需要实时操作
- 战斗自动进行
- 看到60秒前的状态完全可以接受
- 类似于"看回放"的体验

对比其他放置游戏：
- 许多挂机游戏甚至是"关闭游戏"后才结算收益
- 能实时看到队友战斗已经是很好的体验

### 4.3 为什么需要服务器托管？

防止队长"绑架"队伍：
- 队长如果长时间离线，队伍无法继续
- 服务器托管确保队伍不会因队长离线而停摆
- 队员的挂机体验不受队长影响

### 4.4 如何防止作弊？

**服务器验证快照**：
- 时间戳检查：不能快进太快
- 伤害检查：不能超出理论最大值
- 进度检查：不能跳过波次

**异常处理**：
- 检测到异常后，立即转服务器托管
- 从上一个合法快照继续
- 记录异常日志，严重时封禁账号

**长期方案**：
- 可以引入"战斗录像"机制
- 服务器可以重放战斗验证结果
- 使用相同的随机数种子和初始状态

## 5. 与单人系统的关系

### 5.1 复用现有系统

**战斗引擎层**（BlazorIdle.Shared）：
```
BattleInstance.cs          ← 单人战斗
MultiBattleInstance.cs     ← 多人战斗 ⭐ 直接复用
DungeonManager.cs          ← 副本管理 ⭐ 直接复用
RngContext.cs              ← 随机数   ⭐ 直接复用
Clock.cs                   ← 时钟     ⭐ 直接复用
```

**唯一新增**：组队战斗的协调和同步逻辑
- `PartyBattleCoordinator`：队长端协调器
- `PartyBattleService`：服务器端服务
- `PartyBattleViewer`：队员端观察器

### 5.2 数据兼容性

**角色数据**：
- 使用相同的 `CharacterData` 结构
- 使用相同的 `Inventory` 系统
- 收益结算使用现有逻辑

**战斗状态**：
- 使用相同的战斗快照结构
- 复用离线战斗的状态保存机制
- 队伍战斗本质上就是"多角色的单人副本"

### 5.3 离线收益复用

**机制复用**：
- 队员离线 = 单人离线
- 使用相同的离线模拟逻辑
- 队员上线后结算个人收益

**区别**：
- 单人：恢复自己的战斗继续打
- 组队：查看队伍战斗进度，领取收益

## 6. 实现复杂度评估

### 6.1 开发工作量

| 模块 | 复杂度 | 工作量 | 说明 |
|------|--------|--------|------|
| 队伍管理API | 低 | 2-3天 | 创建、加入、邀请、解散 |
| 队长战斗协调器 | 中 | 3-4天 | 本地运行战斗，上传快照 |
| 服务器战斗同步 | 中 | 3-4天 | 验证快照，分发收益 |
| 服务器托管模式 | 高 | 5-6天 | 后台运行战斗，管理队伍 |
| 队员观战UI | 低 | 2-3天 | 显示战斗状态，领取收益 |
| 防作弊验证 | 中 | 3-4天 | 快照验证逻辑 |
| 数据库设计 | 低 | 1-2天 | 新增队伍相关表 |
| **总计** | - | **19-26天** | 约1个月工作量 |

### 6.2 对比方案B（纯服务器）

如果实现纯服务器模式：
- 需要后台任务管理器：5-7天
- 需要高效的战斗调度：3-4天
- 需要优化服务器性能：5-7天
- 需要处理大量并发战斗：3-4天
- **总计**：16-22天

**结论**：混合模式和纯服务器模式开发工作量相近，但混合模式运行成本更低，用户体验更好。

### 6.3 对比方案C（镜像模式）

如果实现镜像影分身：
- 获取角色快照API：1-2天
- 假组队逻辑：2-3天
- UI展示：1-2天
- **总计**：4-7天

**结论**：镜像模式最简单，但不是真正的多人战斗。可以作为"快速原型"或"备用方案"。

## 7. 总结

### 7.1 推荐方案
**混合客户端-服务器模式（方案A）** 是最佳选择：
- ✅ 复用现有战斗引擎，无需重写
- ✅ 低服务器负载，可扩展性强
- ✅ 用户体验好，队长实时战斗
- ✅ 支持离线挂机，队员无压力
- ✅ 实现复杂度适中，可控

### 7.2 实施路径
1. **原型阶段**：先实现镜像模式（1周），验证玩法
2. **MVP阶段**：实现混合模式核心功能（3周）
3. **完善阶段**：添加防作弊、托管、优化（2周）
