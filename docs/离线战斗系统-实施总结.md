## 核心功能实现概览

### 1. 完整状态保存（每30秒）

**实现位置**：
- 前端：`HeartbeatService` 
- 后端：`GameStateController` + `GameStateService`
- 数据库：`GameStates` 表

**保存内容**：
- 副本进度（当前波次、总波次）
- 敌人状态（血量、数量）
- 玩家状态（血量、攻击进度）
- 战斗时钟和随机数种子
- 掉落统计

### 2. 离线战斗模拟

**实现位置**：
- 前端：`StateRecoveryService`
- 后端：`OfflineBattleSimulator`
- **共享代码**：`BlazorIdle.Shared/Game/` 战斗引擎（前后端复用）

**代码复用策略**：
- 战斗核心逻辑（`BattleInstance`、`DungeonManager` 等）位于 `BlazorIdle.Shared`
- 前端和后端都引用相同的代码，**无需重复实现**
- 服务器端仅负责状态重建和模拟调度

**混合模拟策略**：
1. **短时间偏差（< 5分钟）**：客户端本地快速推进，无需服务器
2. **中等离线（5分钟 - 1小时）**：客户端模拟，服务器可选验证
3. **长时间离线（> 1小时）**：服务器端模拟，返回最终状态

**工作流程**：
1. 登录时从数据库加载上次保存的状态
2. 计算离线时长
3. 根据时长选择客户端或服务器模拟
4. 计算离线收益（金币、掉落物）
5. 恢复到当前应有的战斗状态
6. 展示离线收益给玩家

### 3. 时间偏差追赶

**实现位置**：
- 前端：`BattleDemo.CheckAndCatchUpTimeDeltaAsync()`

**触发条件**：
- 本地时间与游戏时间偏差 > 5秒
- 典型场景：切换标签页、浏览器休眠

**处理方式**：
- 短时间偏差（< 1分钟）：客户端本地快速推进
- 长时间偏差（> 1分钟）：调用服务器模拟

### 4. 顶号功能

**实现位置**：
- 后端：`SessionService`
- 前端：`SessionManagementService`

**工作机制**：
1. 用户登录时创建新会话
2. 检查该用户是否有活跃会话
3. 如有，将旧会话标记为失效
4. 旧会话下次心跳时收到410响应
5. 前端显示"被顶号"提示，强制登出

### 5. 版本控制与自动清理

**版本控制**：
- 每个状态记录保存软件版本号
- 加载时检查版本兼容性
- 主版本不同则删除旧状态

**自动清理**：
- 后台服务每小时清理一次
- 清理过期状态（默认保留7天）
- 清理不活跃会话（默认24小时）

## 关键技术点

### 1. 代码共享架构（重要！）

**挑战**：服务器端模拟需要复现前端战斗逻辑

**解决方案**：将战斗引擎迁移到 `BlazorIdle.Shared` 项目
- **前端**（Blazor WebAssembly）和**后端**（ASP.NET Core）都引用 `BlazorIdle.Shared`
- 使用**完全相同的代码**进行战斗模拟
- 无需在服务器端重复实现战斗逻辑

**优势**：
- ✅ **代码复用**：一份代码，两端使用，避免重复开发
- ✅ **结果一致**：前后端使用相同逻辑，保证模拟结果100%一致
- ✅ **易于维护**：战斗逻辑更新时，只需修改一处
- ✅ **降低bug**：避免前后端逻辑不同步导致的问题
- ✅ **性能优化**：共享代码可在两端同时受益于优化

**代码结构**：
```
BlazorIdle.Shared/              ← .NET Standard 2.1 类库
├── Game/                       ← 战斗引擎（前后端共享）
│   ├── BattleInstance.cs
│   ├── DungeonManager.cs
│   ├── MultiBattleInstance.cs
│   └── ...
├── Models/                     ← 数据模型
└── DTOs/                       ← 传输对象

BlazorIdle/                     ← Blazor WebAssembly 前端
└── 引用 BlazorIdle.Shared

BlazorIdle.Server/              ← ASP.NET Core 后端
└── 引用 BlazorIdle.Shared
```

### 2. 战斗状态序列化

**挑战**：完整保存战斗状态，包括时钟、随机数、队伍等

**方案**：
- 使用JSON格式存储
- 设计清晰的状态数据结构
- 支持部分状态（仅保存必要信息）

### 3. 战斗状态恢复

**挑战**：从JSON数据重建完整的战斗实例

**方案**：
- 扩展 `BattleInstance` 和 `DungeonManager` 支持状态恢复（在 `BlazorIdle.Shared` 中）
- 保存并恢复时钟和随机数生成器状态
- 验证恢复后的状态与保存时一致
- **前后端使用相同的恢复逻辑**，确保一致性

### 4. 快速战斗模拟

**挑战**：短时间内模拟长时间的战斗

**混合策略方案**：
1. **客户端本地模拟**（优先级高）：
   - 适用于短时间偏差（< 5分钟）
   - 使用 `BlazorIdle.Shared` 战斗引擎
   - 无渲染模式，快速推进
   - 无需网络请求，响应迅速

2. **服务器端模拟**（长时间离线）：
   - 适用于长时间离线（> 1小时）
   - 同样使用 `BlazorIdle.Shared` 战斗引擎
   - 无渲染模式运行战斗
   - 使用较大的时间步长（100ms）
   - 限制最大模拟时长（24小时）
   - 异步执行避免阻塞

**性能优化**：
- 无UI更新，纯计算
- 批量处理战斗tick
- 可选：跳过某些动画和特效计算

### 5. 顶号实现

**挑战**：实时检测和通知被顶号的用户

**方案**：
- 会话心跳机制（30秒一次）
- 返回特殊状态码（410 Gone）
- 前端监听并显示提示
- 可选：使用SignalR实现实时推送

### 6. 版本兼容性

**挑战**：软件更新后旧状态可能不兼容

**方案**：
- 语义化版本控制
- 主版本不同则删除旧状态
- 次版本尝试兼容加载
- 可选：实现数据迁移逻辑
- **优势**：因为前后端使用相同代码，版本同步更容易

## 潜在风险与对策

### 风险1：状态数据过大

**风险描述**：完整的战斗状态可能占用较多存储空间

**对策**：
- 仅保存必要信息
- 压缩JSON数据
- 定期清理旧状态
- 监控数据库大小

### 风险2：模拟性能问题

**风险描述**：长时间离线的模拟可能很慢

**对策**：
- 限制最大模拟时长
- 优化战斗计算逻辑
- 异步执行不阻塞用户
- 显示进度提示

### 风险3：数据同步冲突

**风险描述**：多端登录可能导致数据冲突

**对策**：
- 实现顶号功能
- 服务器为唯一数据源
- 客户端状态仅用于显示
- 定期同步确保一致性

### 风险4：作弊风险

**风险描述**：离线模拟可能被利用刷收益

**对策**：
- 服务器端验证所有状态转换
- 时间戳验证防止时间回滚
- 限制离线收益上限
- 记录异常行为用于审计
