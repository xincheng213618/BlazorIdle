# 多人战斗系统设计文档

## 文档概述

本文档集提供了BlazorIdle游戏多人组队战斗系统的完整设计方案。该系统专为放置/挂机类游戏设计，支持多人组队副本战斗，同时保持离线挂机的游戏特性。

## 核心特性

- ✅ **多人组队挂机**：3-5人组队进行副本战斗
- ✅ **离线收益**：队员可以离线，上线后领取收益
- ✅ **低延迟要求**：不需要即时操作，适合异步更新
- ✅ **代码复用**：复用现有的 `MultiBattleInstance` 战斗引擎
- ✅ **防作弊**：多层验证+服务器托管保障公平性
- ✅ **简化实现**：避免复杂的SignalR，使用REST API + 轮询

## 🆕 最新推荐架构：服务器权威并行模拟模式（方案D）⭐⭐⭐⭐⭐

### 核心思路
- **服务器和所有客户端同时运行相同的战斗**
- 使用**统一参数**（RNG种子、角色快照、副本配置）
- **服务器结果为最终权威**，客户端结果仅用于动画展示
- 玩家刷新/离线后，直接从服务器恢复状态
- 完全避开SignalR复杂性，使用简单的REST轮询

### 架构优势（相比其他方案）
- 🌟 **所有玩家实时体验**：ABC都在本地运行，都很流畅
- 🔒 **绝对权威防作弊**：服务器独立运算，客户端无法作弊
- 🎮 **优雅的断线恢复**：刷新页面直接从服务器恢复
- 💡 **实现简单**：不需要SignalR，复用现有引擎
- 🚀 **性能可控**：服务器负载可预测，易于优化

👉 **详见** [第六部分：方案D - 服务器权威并行模拟](./6-方案D服务器权威并行模拟.md)

## 备选架构：混合客户端-服务器模式（方案A）

### 核心思路
- **队长客户端**作为"主机"运行战斗（本地）
- **定期同步**战斗快照到服务器（每30秒）
- **服务器验证**快照并分发收益给所有队员
- **队长离线时**，服务器自动接管战斗（托管模式）
- **队员客户端**轮询查看战斗进度（每60秒）

### 架构优势
- 🚀 **低服务器负载**：队长在线时服务器只做验证
- 🎮 **队长体验好**：本地运行，实时反馈
- 😌 **队员无压力**：可以离线，收益照常
- 🔒 **防作弊完善**：服务器验证+托管兜底
- 📈 **高可扩展性**：单服务器可支持100+队伍

## 设计亮点

### 1. 并行模拟（方案D核心创新）✨✨✨
服务器和所有客户端同时运行战斗，服务器结果为准，客户端负责展示。完美结合实时体验和绝对权威。

### 2. 代码复用 ✨
前后端使用相同的战斗引擎（`BlazorIdle.Shared`），无需重复实现战斗逻辑。

### 3. 确定性战斗引擎 ✨
相同的RNG种子+参数=相同的战斗结果。这是方案D可行的技术基础。

### 4. 异步多人 ✨
5-10秒轮询适合挂机游戏节奏，无需复杂的实时通信，大幅降低实现难度。

### 5. 离线友好 ✨
所有队员都可以离线，战斗继续进行，上线后领取收益。真正的"挂机"多人游戏。

### 6. 优雅的断线恢复 ✨
刷新页面直接从服务器恢复状态，玩家只会感觉"稍微卡了一下"，体验自然流畅。

## 常见问题

### Q1: 为什么不用SignalR？
A: SignalR适合需要即时反馈的游戏（如动作游戏）。放置/挂机游戏不需要即时操作，5-10秒轮询已足够，且大幅简化实现。

### Q2: 方案D的客户端结果和服务器不一致怎么办？
A: 
1. **概率极低**：使用相同RNG种子和参数，确定性引擎保证结果一致
2. **玩家心理**：如果不一致，玩家会认为是"网络卡顿"，可接受
3. **最终权威**：以服务器结果为准，客户端只负责展示动画
4. **检测机制**：客户端定期上传checksum，服务器检测异常

### Q3: 方案D的服务器负载会不会太高？
A: 
- 单次战斗tick仅需~10ms
- 100ms tick频率足够精确（10 ticks/秒）
- 单服务器理论容量：50-100个并发战斗
- 可以优先级调度、异步处理、横向扩展
- **比方案A更可预测**，因为不依赖队长在线状态

### Q4: 为什么方案D比方案A更好？
A: 
- ✅ **所有玩家实时体验**（不只队长）
- ✅ **服务器绝对权威**（无需验证机制）
- ✅ **断线恢复优雅**（直接从服务器获取）
- ✅ **实现更简单**（无需队长权限管理和托管切换）
- ✅ **5周vs7-8周**（开发更快）

### Q5: 方案D有什么风险？
A: 
- 服务器负载需要实际测试验证（建议压力测试）
- 客户端性能差异可能导致动画卡顿（但不影响结果）
- 需要确保战斗引擎确定性（已有RngContext，问题不大）

### Q6: 如何选择方案？
A: 
- **推荐方案D**：体验最好，实现最简单，5周完成
- **备选方案A**：如果担心服务器负载，可以选这个
- **保险方案C**：1周MVP，快速验证玩法可行性
